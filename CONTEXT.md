# webtweak

A local, open-source visual editor for hand-coded HTML/CSS pages. You manipulate an existing page visually (resize, restyle, nudge, change fonts); webtweak captures what changed as machine-readable patches; Claude reconciles those patches into the real source files and pushes. Built as a free alternative to paid visual editors like Pinegrow, for hand-coded editorial sites, exploiting the fact that a human-plus-Claude loop means the editor only has to *capture intent*, not flawlessly rewrite source.

## Language

**Project**:
The directory webtweak is operating on. It supplies the set of pages you can open without choosing another Project. Membership is by file location, not by what the site links to, so a page nothing links to is still a page. Stylesheets and assets are not members; they are found through whichever Target page is open. A Project is selected, never declared - there is no project file.
_Under review_: exactly which files qualify, how the directory is resolved from a command line, and whether switching Project is a privileged act. See the Project decision below.
_Avoid_: site (ambiguous between source, built output and the deployed result), workspace (suggests saved editor state), repo (a repository may hold several Projects, or none), root or web root (server and filesystem roles, not this concept)

**Target page**:
The page in the Project currently open in the Overlay. webtweak edits one Target page at a time; opening another Target page does not change the Project.
_Avoid_: live site, URL, deploy

**Overlay**:
The editing UI injected on top of the Target page in the browser - element picker, drag/resize handles, properties panel.
_Avoid_: editor (too vague), canvas

**Patch**:
One captured change to one element - the element's identity plus the property/value that changed.

**Fingerprint**:
The bundle of signals a Patch carries to identify its element without mutating source - tag, id, classes, truncated text and own-text, a clean opening tag (`openTag`, inline `style` stripped), and a positional CSS `selector` used only as a weak tiebreaker. Claude locates the element in real source by matching the whole bundle, the way a human would.

**Edits file**:
The file webtweak writes containing all Patches, the hand-off artefact Claude reads. On disk it is named `<page-stem>.webtweak.json`, next to the Target page. (There is no file literally called `edits.json`; "edits file" is the abstract term.) The on-disk layout stated here is **current 0.8.x behaviour, not a settled 1.0 answer** - whether there is one edits file per page or one per Project is [issue #9](https://github.com/stueydubs/webtweak/issues/9), still open. Read this entry as a description of today, not as a decision.

**Batch**:
One editing session's worth of Patches inside the edits file, stamped with viewport + timestamp and a status of `pending` or `reconciled`. Claude only applies `pending` Batches; reconciled ones stay as history.

**Reconcile**:
Claude's half of the loop - reading the edits file and applying the Patches cleanly into the real source files (proper CSS, house conventions). Reconcile stops at source; it does not push.
_Avoid_: merge, sync

**Band**:
One width range an edit can be scoped to, taken from the Target page's own media queries - `(max-width: 600px)`, or `base` for "every width". The Overlay reads the page's declared conditions rather than offering a device list, so an edit lands inside the site's existing responsive system instead of adding a breakpoint nobody asked for. **Scope** is the name of the picker that selects one (it reads *Applies at*, because the Band is the condition a change is written under, not the thing being edited); **media group** is the Band once serialised, one entry in a Patch's `media` map keyed by the condition text. Not every control is bandable - Border, per-side spacing and every shape control stay base-only, and the panel says so.
_Avoid_: breakpoint (that is the page's own CSS boundary, not the range between two of them), viewport (that is the window width you are authoring at), device

**Peek**:
Making the whole Overlay invisible so the Target page underneath can be seen and clicked - toggled with `H`, and ended by the click that selects whatever was covered. It exists because the chrome does not merely obscure the page, it takes the page's clicks: without it, nothing under the bar, the properties panel or the change list can be selected at all. A peek changes nothing about the page - no offset, no reflow - so what you see under the chrome is what the page really renders.
_Avoid_: hide/collapse (those suggest the chrome shrinks or stays gone), preview mode

**Border**:
A CSS `border` on an ordinary page element - composed in the panel from Width, Style and Colour, and emitted as one declaration (or a per-side `border-bottom` when the element carries a rule on one side only).
_Avoid_: using it for a shape's outline, which is a Stroke

**Stroke**:
A shape's outline - the SVG `stroke`/`stroke-width` on a created shape's `<svg>`. Distinct from Border by design, not by accident: ADR-0002 chose SVG precisely so a real outline renders on every shape kind, and a CSS border on the wrapper would draw a rectangle around a triangle. The panel's shape controls are therefore labelled Stroke and Stroke width, and the Border group hides for shapes. A shape's **Radius** keeps that name, because `rx` and `border-radius` are the same concept in the same units.
_Avoid_: border, outline

## Relationships

- A **Project** holds many pages; exactly one of them is the **Target page** at a time
- When webtweak's own server is doing the serving, the **Project** directory is what it serves as the web root. That is a fact about today's runtime, not part of what a Project is - a later dev-server proxy mode would change the serving without changing the Project
- A **Target page** is edited via the **Overlay**, producing one or more **Patches**
- Each **Patch** carries base declarations, plus one **media group** per **Band** the edit was scoped to
- **Patches** are serialised into the **Edits file** (`<page-stem>.webtweak.json`)
- Claude reads the **Edits file** to **Reconcile** changes into the **Target page**'s real source, folding each media group into the `@media` block that already governs its **Band**

## Decisions captured

- **Element identity is a rich Fingerprint**, not a single selector and never an injected attribute. webtweak captures tag + id/classes + truncated text/ownText + a clean opening tag (`openTag`, inline `style` stripped) + siblingIndex + best-effort selector; Claude matches the bundle. Source is never mutated until Reconcile. Genuinely ambiguous cases (identical siblings) are flagged back to the user, not guessed.
- **Property scope is appearance + layout only.** Editable: typography (font-family, font-size, font-weight, line-height, letter-spacing, colour, text-align), box (width, height, margin, padding), background-colour, **border, corner radius and box-shadow** (added in 0.4.0), and a position nudge. Font is picked from a list of the Target page's own font stacks; shadow from a list of presets; both lists still accept free text. Still excluded: flex/grid alignment editors, hover/focus states, pseudo-elements, per-corner radii, per-side border controls, and editing text copy (copy changes are spoken to Claude, not done in the Overlay). No structural DOM reordering.
- **Border is composed from three controls and seeded so every control is visible.** Width, Style and Colour write one `border` declaration, and touching any of them on a border-less element seeds the other two - because a colour alone and a width alone both render nothing while the initial style is `none`, and recording an invisible change is the phantom-patch failure this codebase keeps re-learning. An element bordered on exactly one side has that side edited instead (`border-bottom`), since composing four sides onto a heading's rule would turn a divider into a box. See [ADR-0003](./docs/adr/0003-compose-shorthands-from-discrete-controls.md).
- **Where the Overlay cannot express what an element already has, it declines the control rather than flattening it.** An element whose four sides carry different borders, or whose four corners carry different radii, has those fields switched off with an explanation - because the alternative is a single value silently replacing a deliberate design (a pair of rules becomes a box; a tab shape becomes a fully rounded one). This follows the older precedent that disables width/height on non-replaced inline elements so a user cannot record a Patch the element will not honour. Per-side and per-corner controls are out of scope, so the honest options are decline or destroy.
- **The Overlay covers the Target page, and that made the covered part uneditable until Peek.** Every piece of chrome is `position: fixed` with `pointer-events` enabled, so page content underneath it could not be clicked to select - and because each is measured from the *viewport*, scrolling never brought the covered rows out from under them. It was never only the bar: measured with `elementFromPoint` on a 4px grid with one element selected, the chrome covers about 27% of a 1280x800 window (bar 44px, panel 270px of the right edge, dock bottom-left) and about 76% of a 360x740 one, where the bar wraps to three rows. Whole numbers deliberately: the grid's own phase moves these by roughly half a point, so a figure quoted to 0.1% is claiming more than the method can support. Three rows at 480px is structural rather than sloppy - eight controls need 472 of the 480px before the reconcile badge has any width at all - so the bar cannot be made short enough to fix this, and a 44px bar still covers the top of a 56px nav. The consequence was worse than "hidden": the click worked whichever control was there, so aiming at a page's top nav opened the shape palette or pressed Undo, at *every* width. **Peek** is the answer to the reachability half, and it hides the chrome rather than moving the page - an offset would have fixed only the bar, would have changed how the page renders, and would not have moved a `position: fixed` header at all. The footprint half was attacked separately and the breakdown decided where: below 520px the properties panel becomes a **bottom sheet**, because a 270px column is 75% of a 360px window while a full-width 45vh sheet costs 45% of any window. Where the two meet depends on how tall the panel actually renders, so it is a band and not a point: at the sampled 0.89 of window height they cross at 534px, and across the range that fraction really takes (0.84 to 0.92) the crossing moves between 504px and 552px. 520 sits inside that band. It is a chosen breakpoint rather than a derived one, and it errs towards keeping the column until the sheet is clearly the cheaper shape. Below 460px the bar gives back a row by letting the crumb share one. Net at 360x740: about 77% down to about 61%, and deliberately unchanged at 1280x900, where the column is already the right shape. See [ADR-0005](./docs/adr/0005-peek-hides-the-chrome-rather-than-moving-the-page.md). What remains true: the Overlay is still most of a small window while you are editing in it, and peek rather than a smaller panel is what gives the page back.
- **Some of the Overlay's layout is measured in JS and published to CSS, because CSS cannot ask the questions involved.** There are three such channels now, each added by a different feature and each rediscovered from scratch, so they are written down here rather than in the next feature's comments. The rule for adding a fourth: if CSS *can* express it, it belongs in `overlay.css`; only genuine "how tall did that actually render" and "did that actually wrap" questions get a channel, and each one needs a named property or class plus the fallback that applies before the first measurement.
  - `--wt-bar-h` - the bar's rendered height. It wraps, so its height is a fact about content, not a constant. Stylesheet default 44px is the one-row fallback.
  - `--wt-panel-h` - the panel's rendered height, read only by the dock in the bottom-sheet layout. Default `0px`, which is exactly right while the panel is hidden.
  - `.wt-bar-wrapped` - set by JS because no media query can ask whether a flex container wrapped, and a dropdown anchored to a control on a middle row has to drop below the whole bar instead. Absent is the fallback, and it is the right one: an unmeasured bar is assumed to be on one row, which is what a bar too narrow to have wrapped yet actually is.

  `chromeFloor()` is *not* one of these and is listed here only so it is not mistaken for one: it publishes nothing to CSS and has no fallback, because the answer depends on which element is being revealed. It belongs to the same family of "CSS cannot ask this" problems and is solved the same way - by measuring rendered boxes rather than restating a number - but it is a function, not a channel.

  Both measured properties ride one `ResizeObserver` deliberately: as two observers the panel's callback wrote a property the bar's callback read, and construction order decided whether the read saw the write.
- **A position nudge is captured as intent, not literal CSS.** webtweak stores a snapped (4px grid) pixel offset `(dx, dy)` from the element's natural position, previewed via `transform: translate(...)`. Claude reconciles small nudges into clean real-CSS (margin/padding/spacing in house conventions); large or flow-impossible drags are flagged as v2 reorders, never baked in as `position: absolute`/`transform` hacks. Trade-off accepted: intent-to-clean-CSS means a nudge may land at a tidy value (12px) rather than the exact drag distance (11px).
- **Stack: Node stdlib only, zero dependencies.** Single `webtweak.js` script over `node:http` (serve directory, inject Overlay, handle one POST to write the edits file). interact.js is vendored locally (not CDN) so the Overlay works offline. Originally a single Python file; rewritten in Node at `cfe23ff` so the tool could ship on npm as `npx webtweak`, since its audience already has Node. The Python reference implementation was kept in parallel for a while and deleted in 0.2.0 once the unit tests were repointed at the shipped Node functions - a second implementation the tests asserted against, but users never ran, made the suite read as safer than it was. The reconcile *helper* (`reconcile/scripts/wtreconcile.py`) is still Python 3, so the full loop needs both runtimes.
- **Reconcile scopes to the single edited element by default, and flags systemic-looking changes.** Default output is CSS targeting only the element you touched (no surprise ripple to siblings sharing a class). When a change looks global (the only paragraph, or every heading changed alike), Claude pauses and asks "just this one or all `.section-title`s?" rather than guessing. Reconcile always writes real CSS rules into the stylesheet already governing the element - never inline styles.
- **Editing is per-breakpoint, against the page's own breakpoints.** The Overlay reads the media queries your stylesheets declare, a **Scope** picker says which **Band** an edit applies at (defaulting to the narrowest that matches your window), and a banded edit previews only inside that band - drag the window out of it and the page returns to base, as it will once reconciled. The Patch carries a `media` map sibling to `changes`, and reconcile merges it into the `@media` block already governing that condition. What stays true: you author at widths your own screen can show, since there is no device frame - you resize your window; and webtweak only ever offers the conditions your page declares, plus one you type by hand. Deciding your site needs a 390px breakpoint is a design decision, not an edit. Type, Colour and Box are bandable; Border, per-side spacing and every shape control stay base-only whatever is picked, and the panel says so rather than quietly ignoring the choice. Shipped in 0.7.0; the viewport stamp survives as a record of the width a session happened at, which is a different thing from the Band an edit is scoped to.

- **The edits file is a running history of Batches, never cleared.** Lives next to the Target page (`<page-stem>.webtweak.json`). Each Save overwrites the current `pending` Batch with a full snapshot of the session's Patches. Reconcile flips the Batch to `reconciled` (timestamped) and leaves it in place; Claude only ever applies `pending` Batches, so stale patches can't re-apply. To keep that history as a version-controlled changelog, commit the edits file **in the site's own repo** (the file lives beside the page being edited, not in the webtweak repo). The webtweak dev repo gitignores `*.webtweak.json` because there it only ever appears as a transient test artefact. Command: `webtweak <path-to-html>`; published to npm, and the dev copy lives at `~/projects/webtweak/`.
- **The server watches the served tree and pushes reloads, so the loop is visible.** Reconcile happens in another window; before this, the user saved and had no signal until they reloaded by hand. webtweak watches its served directory and sends events over SSE (`GET /__webtweak__/events`); a clean page reloads itself, so a reconcile lands in front of the user, and a **reconcile badge** reflects the edits file's own view (`N pending` until Claude flips the batch to `reconciled`). **Three rules make it safe**, and the third is the subtle one:
  1. A reload **never** runs over unsaved edits. Guarded on `dirty`, not on "has edits" - after a Save the batch is on disk and `restore()` re-applies it, and reloading after a save is exactly the case that matters.
  2. webtweak's own temp/backup artefacts are excluded, or every Save would bounce the page being edited.
  3. **A reload never runs while this session's Batch is still `pending`.** Reconcile writes source *first* and marks the Batch *second* (SKILL.md steps 7 then 9), so there is a window where the CSS is already rewritten but the Batch still says pending - and `restore()` would re-apply it on top, doubling a nudge and re-emitting the same Patches on the next Save. This is a **cross-component ordering coupling**: it depends on reconcile's step order, and if reconcile ever marked *before* writing, the Overlay would double-apply silently. The Edits file is therefore watched as its own `edits-change` event (a mark touches only that file, so without it the badge could never reach `reconciled`), with webtweak's own save recognised by comparing the exact bytes it wrote.

  Watching is per-directory rather than `fs.watch(recursive)`, which only reached Linux in Node 20 while the package supports 18; if watching fails the tool degrades to no live reload, never to a crash.
- **Input is local source files**, not deployed URLs. webtweak opens the actual `.html` on disk and serves one directory around it - in 0.8.x the page's own folder by default, or `--root DIR` when the page sits in a subfolder and references root-absolute assets (`/css/site.css`). From 1.0 that directory is the **Project** and is chosen up front rather than inferred from the page; see the Project decision below, which supersedes this sentence's account of how the served directory is picked. The Edits file always lands beside the *page*, not in the served root. (Caveat: pages needing a build step - Tailwind compile, partials - may not render identically to production; a non-issue for hand-coded editorial sites.)
- **Shape creation is webtweak's first element-creation feature, via a `create` Patch op.** You can draw decorative shapes (square, circle, triangle, star, pentagon, hexagon) onto the page, dragging to set the size; each is one inline `<svg>` (uniform renderer, so a real stroke renders on every shape and `fill`/`stroke`/`stroke-width` cascade from the wrapper to the child). A shape drops at the click point as a `position: absolute` element - the sanctioned exception to the no-`position:absolute` rule, which governs flow content + nudges, not a genuine decorative absolute layer. A shape can be turned in 45° steps (`transform: rotate(Ndeg)`), which is what retired the `rectangle`, `ellipse` and `diamond` kinds - each was a stretched or turned version of one of the six, and drag-to-draw plus rotation express all three. A shape reuses the whole existing Patch/select/resize/undo/restore machinery, marked `e.shape`, and on Save emits `{ op: "create", shape, geometry, anchor, fingerprint, changes }` (self-contained; server stores it verbatim). **Self-contained is load-bearing, not decorative:** because the patch carries its own `geometry`, restore rebuilds a shape whose kind this build has never heard of - which is why retiring three kinds did not silently redraw every saved diamond as a square. Reconcile learns to *insert* clean source for it, stripping the throwaway `wt-shape-<rand>` id. See [ADR-0002](./docs/adr/0002-shape-creation.md). This narrows but does not close ADR-0001: webtweak still never rewrites existing source - it only appends a self-contained new element for Claude to reconcile.
- **The served page is trusted, and that is the tool's real trust boundary.** The server binds loopback, refuses a forged `Host` (DNS rebinding), refuses a cross-origin `Origin` on `/save`, `/edits` and `/events` (CSRF), contains every path twice (resolve, then realpath), and now refuses any `.`-prefixed segment so a `--root` pointed at a site root does not hand out `.git/`. All of that defends against *other* pages. It cannot defend against **this** one: the target page's own `<script>` is same-origin with the save endpoint by construction, so it can POST a forged Batch with no token, nonce or user gesture. A per-session token would be theatre - the Overlay has to read it from the page, so anything else in the page can read it too. Process isolation is the only real answer and it is out of scope for a local dev tool.

  So the mitigation is placed where it can actually work: the *reconcile* half treats the Edits file as **captured data, never instructions** (SKILL.md states this and names the fields it may read), because that file is what an agent later folds into real source, and it is the highest-value write target in the whole tool. `tests/test_e2e_untrusted_page.py` covers a narrower thing - that the Overlay will not execute markup held in an element's `id`/`class` - which is worth having but is not this. Judgement, stated plainly: opening a page you do not trust means running its JavaScript, which is true of every browser; what webtweak adds is that the same page can queue instructions for an agent, and that is the part worth being explicit about rather than papering over.
- **A Project is a directory webtweak is operating on, and it is the unit webtweak opens.** Opened on [issue #5](https://github.com/stueydubs/webtweak/issues/5) for 1.0; nothing here is built yet, and **the ticket was reopened after adversarial review**, so read the split below carefully rather than treating the whole thing as settled.
  - **Settled: identity is selection, not detection and not declaration.** A Project is the directory webtweak was told to operate on. Detection was rejected because it has false negatives on exactly this audience - a hand-coded editorial site may have no `.git` and no root `index.html`. Declaration was rejected because a folder without the file would then be somehow less of a Project.
  - **Settled: membership is by file location, not by link graph.** A page nothing links to is still a page, because the single likeliest page you want is the draft you have not linked yet, and reachability only works if the nav is in plain HTML rather than a partial. Stylesheets and assets are not members; they are already reached *through* the open Target page, since the Band picker reads the page's own media queries and the font list its own stacks, so a Project-level view of CSS would be a second thing to keep truthful for no gain.
  - **Settled: no Project file in your site repo.** A config file is easy to add and effectively impossible to remove once people commit it, and it would contradict selection-not-declaration directly. The only *Project metadata* on disk is machine-local (the picker's recents list), which is a fact about your machine and not about the site. Note the wording: Edits files are also disk state and are deliberately committed to the site's repo, so "no disk state" would be false.
  - **Settled: a wrong root is not guessed at from the source.** An earlier draft scanned the page for `href="/..."` and refused to start on a hit. Dropped, and it should stay dropped: a false positive there gates a *refusal*, and the regex false-positives on protocol-relative CDN links (`src="//cdn..."`), on a bare `href="/"` home link and on commented-out markup, while still missing root-absolute URLs inside CSS and JS.
  - **Reopened: which files qualify.** The first draft said "every eligible `.html`", excluded `node_modules`, `dist`, `build` and dot-prefixed, and justified ignoring `.gitignore` on the grounds that some sites keep their only real pages in `dist`. Those last two contradict each other outright - under that rule such a site has zero pages. Unresolved with it: `.htm` and extension case, which `webtweak.js` already accepts and case-folds; symlinks whose real target leaves the Project, against the server's existing realpath containment; and the fact that `isSkippedDir` skips only `node_modules` and dot-prefixed, so enumeration and watching would disagree. Scale is real but is a *separate* fact from membership: the watcher caps at `MAX_WATCHED_DIRS` and `MAX_WATCH_DEPTH` and degrades to a startup note, so "pages in the Project" and "files being watched" are not the same set and the definition must not imply they are.
  - **Reopened: how the command line resolves a Project**, and whether an explicit choice can ever be overridden. The first draft had a page named outside the Project silently fall back to that page's own folder. That contradicted its own rule that naming a page never sets the Project; it made `--root`'s meaning change rather than survive, since today `--root` strictly refuses a page it does not contain; and it *widened* exposure against 0.8.x, because `webtweak page.html` would serve the current folder instead of the page's folder, so running it from a home directory would serve the home directory to a page that can forge requests. Printing the chosen directory is notification, not consent.
  - **Reopened: whether switching Project is a privileged act.** The first draft assumed that activating an *already-known* Project from a server-owned recents list was harmless, and that the danger was only in an endpoint accepting a client-supplied path. That assumption does not survive the trust-boundary decision above: a hostile page that asks to open a known Project keeps running across the switch on an unchanged origin, and can persist via a registered service worker. Recents entries are capabilities to previously authorised roots, not inert UI state.
  - **Missing entirely from the first draft:** which page opens when no page is named, whether a Project may have no Target page at all, and what happens to unsaved edits, a `pending` Batch, the watcher and the SSE connection when the Target page changes.
- **Non-UTF-8 pages are served byte-for-byte** under their own declared charset. Reading HTML as a UTF-8 string decoded with replacement characters and re-encoded, which destroyed the original bytes rather than mislabelling them - and because the Fingerprint carries the element's truncated text, every Patch on a windows-1252 page then held `caf�` and could never be matched back to source. HTML is read as a Buffer and spliced through `latin1` (byte-transparent), and `charsetOf` honours the document's own `<meta charset>` instead of asserting UTF-8 over it.
