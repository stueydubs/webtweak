# Breakpoint-scoped Patches: the page's own media queries, previewed with an injected style block

Per-breakpoint authoring (0.5.0) is the first feature that cannot be expressed in the Patch contract as it stands. A Patch says "this element, this property, this value"; a responsive edit says "this element, this property, this value **at this width**". We decided a Patch gains a **media dimension** - `changes` continues to carry base declarations, and a sibling `media` map carries one group of declarations per media condition - and that a breakpoint-scoped edit is previewed by an **injected `<style>` element containing real `@media` blocks**, because an inline style cannot be media-conditional.

This is the first change to the Patch contract in the project's history, and 0.4.0 deliberately avoided touching it, so it gets an ADR rather than a changelog line.

**Why not a device frame.** The obvious design is a resizable iframe with the Target page inside it, the way every commercial visual editor does responsive. It was rejected because the Overlay is *injected into the page* and reads `getComputedStyle` directly on the page's own elements. Moving the page into a frame makes every read, every fingerprint, and every event cross-document, and turns the Overlay from an injected script into a parent-document application driving a child - a re-architecture, not a feature. The user's own window is already a viewport. Trade-off accepted: you can only author at widths your screen can actually show, and you resize your own window (or use the browser's device mode) rather than picking a device from a menu. That is an honest limitation, not a hidden one, and it keeps the tool the size it is.

**Why the page's own breakpoints, and not a list of devices.** Offering "iPhone 14 - 390px" invites a media query at 390px on a site built around 480/768/1024, which quietly adds a fourth breakpoint nobody asked for and fragments the stylesheet the tool is meant to respect. The page already declares its own system, and the Overlay can read it: a browser prototype confirmed `CSSMediaRule.conditionText` returns each query verbatim, gathered with the same defensive try/catch the font picker uses for `@font-face`, so an unreadable CDN sheet degrades the band list rather than throwing. When nothing is readable, the user types a condition by hand - the list is a convenience, never a gate, exactly as the font list is.

**Which band, when several match.** At a 480px window, a prototype found both `(max-width: 900px)` and `(max-width: 600px)` matching at once. So "the current breakpoint" is not a single thing, and picking wrongly writes the edit into a query that also governs widths the user was not looking at. The editing target is therefore **explicit and visible**, defaulting to the *narrowest matching* band - the most specific, and the one someone who has just dragged their window narrow is thinking about - with every declared band listed and the matching ones marked. Base is always available as a target, including while a narrow band matches, because fixing a base style you happen to be viewing narrow is a legitimate thing to do.

**Non-width conditions are declined, not offered.** The same sweep finds `print`, `prefers-color-scheme`, `hover` and friends. None of them can be previewed by resizing a window, so an edit targeted at one would record a change the user never saw - the phantom-Patch failure the Overlay guards against everywhere else. They are listed as unavailable with the reason, following the mixed-side border guard: decline out loud rather than lie.

**How a scoped edit is previewed.** An inline `style` attribute cannot carry a media query, so the existing preview mechanism cannot express a banded edit at all. The Overlay instead maintains one injected `<style>` element holding real `@media` blocks, and gives each element it edits in a band a generated `wt-mq-N` class to target. A prototype confirmed the obvious-but-necessary point: the rule applies at 480px and does not apply at 700px or 1280px, so the preview is conditional in exactly the way the recorded Patch claims.

Two properties of the existing design make this safe. First, `getComputedStyle` already resolves the page's own media queries at the current width, so the panel populates with band-correct values for free - the prototype watched the fixture's headline read 44px at 1280px and 32px at 480px with no extra work. Second, `nonWtClasses` strips only the exact class names registered in `WT_OWN_CLASSES`, deliberately not a `wt-` prefix match (a prefix match would erase a page's own `wt-` design-system classes from its Fingerprint). Each generated `wt-mq-N` is registered there as it is created, so the preview hook can never reach a Fingerprint. ADR-0001 still holds: no injected identity, no source rewriting, nothing persisted to the page.

## Consequences

- **Reconcile must merge into existing `@media` blocks rather than appending new ones**, and must not reorder them - media query order is cascade order, so moving a block changes which rule wins. A new block is created only when the page genuinely has no query for that condition, and then placed by the site's own convention (usually after the base rules it modifies).
- **The Edits file gains a dimension, backward compatibly.** A patch with no `media` key is exactly what 0.4.0 wrote, so existing edits files keep reconciling unchanged, and the reconcile skill branches on presence rather than on a version number.
- **Undo, the change list and revert become band-aware.** `font-size` at base and `font-size` at `(max-width: 600px)` are two different recorded values on the same element and the same property, so every structure keyed by `el + prop` needs the band as part of its key. This is where the release's silent failure lives: a banded edit overwriting a base edit would still produce a valid-looking Patch, the same shape of bug ADR-0003 warned about for composed borders.
- **Restore-after-reload must re-apply banded groups through the injected style block**, not as inline style, or a restored mobile edit would appear at every width.
- **The batch's `viewport` stamp keeps its job** for base edits - Claude still warns when a base change authored at a wide window would obviously break narrow - but it stops being the only responsive signal, and a banded edit needs no such warning because the user said which width they meant.
- **Only widths the screen can show are authorable.** A 320px band cannot be previewed on a laptop without the browser's own device mode. The Overlay says so rather than pretending, and the manual-condition path means the edit is still *recordable* if the user knows what they want.
