# Peek: the Overlay's chrome gets out of the way, rather than the page being pushed out from under it

The Overlay covers a substantial part of the viewport, and everything under it is not merely hidden but **unselectable** - a click there works a control instead of picking the element beneath. We decided the fix is **peek**: one key (`H`) makes the whole chrome `visibility: hidden`, a click then reaches whatever was underneath and selects it, and the chrome comes back with that element selected. The page's own layout is never touched.

This is a bug fix that needed a design decision, which is why it gets an ADR rather than a changelog line: the obvious fix is a different one, and it is wrong for reasons that only show up once measured.

**The measurement, because the size of it is the argument.** Sampling `elementFromPoint` on a 4px grid across the whole viewport, with one element selected so the properties panel is open:

| Viewport | Chrome, idle | Chrome, with a selection |
|---|---|---|
| 1280x800 | ~8% | ~27% |
| 1440x900 | ~7% | ~24% |
| 480x800 | ~7% | ~58% |
| 360x740 | ~12% | ~76% |

Whole numbers, and the approximation is the honest form. A 4px grid is a sample, and its own phase against the chrome's edges moves each figure by roughly half a point - re-sampling gave 27.3% where the first run gave 27.7%. The argument here rests on the difference between 27% and 76%, which no amount of grid phase touches; a tenth of a percent would be borrowed precision, and the first draft of this table quoted one.

And the reachability half, on a page whose `nav` occupies its top 56px, clicked at four widths with a fresh page each time: the click hit `wt-shape-btn` at 360px, `wt-undo` at 480px, `wt-shape-btn` at 700px and `wt-scope-input` at 1280px. Never the nav. A top nav - the single most common thing at the top of a page - could not be selected at **any** width, and the click was not even inert: it opened the shape palette or pressed Undo. The panel does the same to a right-hand rail (a click landed in the line-height field) and the dock to a bottom-left widget.

**Why not push the page down.** The obvious fix is `padding-top: var(--wt-bar-h)` on the page, and the bar height is already measured and published as that property, so it is nearly free. It was rejected on three counts, in increasing order of seriousness:

1. **It is half a fix.** It addresses the bar and does nothing at all for the panel (270px of the right edge) or the dock. Those are the larger share of the ~27%.
2. **It changes how the page renders**, which is the one thing this tool exists not to do. A full-bleed hero designed to touch the viewport top no longer does; `100vh` sections overflow by the bar's height; and the offset is present in every judgement the user makes by eye, which is the only way they make judgements here.
3. **It does not move the element most likely to need it.** A `position: fixed` header is anchored to the viewport rather than the document, so it stays exactly where it was - under the bar. The offset rescues everything except the case that motivated it. (Not `position: sticky`, which was named here at first and does not belong: a sticky header is in normal flow until it sticks, so `padding-top` on the page moves it like anything else. `fixed` alone carries this argument, and it carries it on its own.)

The same reasoning that rejected the device frame in ADR-0004 applies: the page is the page, and the Overlay is a guest in it.

**Why not simply make the bar shorter.** This was the original request, and it treats the symptom. The bar is 90px when wrapped and 44px on one row, and a 44px bar still makes a 56px nav unselectable at its centre - so shedding controls into an overflow menu would buy back the nuisance while leaving the hole exactly where it was. It also does nothing for the panel or the dock. Worth doing on its own merits one day; it is not this.

**Why a deliberate toggle rather than an automatic reveal.** Auto-hiding the chrome when the pointer nears it, or when the user "seems to be reaching for something underneath", requires guessing intent, and guessing wrong means the Overlay disappears while someone is aiming at Save. A key the user presses is predictable, and predictability is worth more here than cleverness.

**Why the click ends the peek.** Reaching a covered element is the reason to peek, so the click that reaches one has finished the job: the chrome returns with the properties panel already open on the element. Pressing `H` again is there for the other use - looking at your own page without the Overlay on top of it - so both intentions have a gesture and neither is inferred.

**`visibility: hidden`, and specifically not the other two ways to hide something.** This is the part that would be silently wrong if chosen carelessly:

- `display: none` takes the bar out of layout, so the `ResizeObserver` that measures it writes `--wt-bar-h: 0px`. The panel, the dock and the place-hint all position against that property, and `.wt-bar-wrapped` is decided by comparing the measured height against `min-height`, so a zero turns that class on for as long as the peek lasts. *This first said the misplacement outlasted the peek and that the bug would surface later looking unrelated. It would not: the same `ResizeObserver` fires again the moment `display` is restored, so the cost is a frame of wrong geometry, not a lasting one. Still the wrong choice, for a smaller reason than the one originally given - and the overstatement is worth leaving on the record, because an argument that has to be inflated to win is worth re-checking.*
- `opacity: 0` leaves the chrome hit-testable and focusable, so the bar goes on swallowing the very click peek exists to let through.
- `visibility: hidden` keeps the box - so the measurement stays right - while removing it from hit-testing and from the tab order both. It also triggers the HTML focus fixup rule, so a bar button that had focus when the peek started hands it back to the body on its own; an explicit `blur()` was written first and then deleted, because it was a line taking credit for the stylesheet's work.

## Consequences

- **`H` is now a reserved key over the page**, so it must be ignored whenever a field has focus - the panel is full of text inputs and a page may hold its own. `Ctrl/Cmd+H`, `Alt+H` and `Shift+H` all fall through to the browser.
- **Every transient layer must close when a peek starts.** The palette and the suggestion lists are anchored to controls that are about to vanish, and each has its own lifecycle, so closing one is not closing the other.
- **The hover box has to be dropped on both edges of the toggle.** `.wt-box` outranks `.wt-bar` inside `#wt-root`'s stacking context, so a box drawn on the nav - which only ever happens while peeking, that being the only time the nav is the pointer's target - paints *on top of* the bar once the chrome comes back, and stays until the pointer next moves.
- **The peek note is the one thing still drawn over the page**, so it is `pointer-events: none` and not `.wt-ui`: it must survive the rule that hides everything else, and it must never re-create the defect in miniature. Because nothing else hides it, it has to hide itself.
- **Esc gains two more precedence levels**, both ahead of the selection: peek, the outermost transient state, and a focused text field, which has to be released before the selection is because the `H` guard tells the user to press `Esc` to get out of one. That makes five layers before `deselect()`. Esc's job throughout the chain is to leave the newest layer rather than the oldest. (This said "a fourth precedence level" while the same change added two of them.)
- **`fixtures/chrome-collision.html` exists to be collided with.** `sample.html` cannot test any of this - its `.wrap` carries 80px of top padding, so its first text clears a 44px bar by accident, and it has nothing at the right edge or the bottom-left corner at all. Each element in the new fixture is positioned under one region of the chrome, and `test_e2e_peek.py` asserts both halves of every pair: that the region really does swallow the element, and that peek really does hand it back. A test proving only the second half would keep passing if the fixture drifted out from under the chrome, which is exactly how this would quietly stop testing anything.
- **Peek makes the page reachable, not the Overlay smaller** - so the footprint was attacked separately, and the breakdown said the bar was never the thing to attack. With an element selected, the panel is roughly 19% of a 1280x900 window against the bar's 5%, and 63% of a 360x740 one against the bar's 12%. Three changes followed, each measured rather than guessed:
  - **The panel becomes a bottom sheet below 520px.** A 270px column is 75% of a 360px window and leaves a 78px strip too narrow to read a layout in. The arithmetic narrows the crossover without settling it. A column costs roughly `(270/w) x 0.89` of the viewport, a full-width 45vh sheet costs `0.45` regardless of `w`, and solving those gives **534px**. But `0.89` is one measurement, not a constant - it is `797/900` from a single 900px-tall window with a one-row bar - and across the range that fraction actually takes, about 0.84 to 0.92, the crossing moves between **504px and 552px**. That is a 48px band, and 520 sits inside it.

  So 520 is a *chosen* breakpoint, not a derived one: it errs towards keeping the column until the sheet is clearly the cheaper shape. Two earlier drafts of this paragraph both overstated the method - the first said the two "meet near 520px", which was simply the lowest width sampled, and the second called the crossover "arithmetic" and put the spread at "a few px". Neither survives recomputation. What the arithmetic genuinely settles is the *direction*, and the direction is what the breakpoint needed. The first draft switched at 620px and made coverage *worse* there, 46.7% to 55.7% - the sheet is only the better shape once the column has stopped fitting.
  - **The dock rides above the sheet**, via a `--wt-panel-h` measured exactly as `--wt-bar-h` is. They share the bottom-left corner, and the sheet's height is a rendered fact: the groups collapse, and it only exists while something is selected.
  - **The bar gives back a row below 460px.** The whole-row crumb is right between 480 and 560, where the controls need two rows regardless so the crumb's row is free, and wrong below 460, where it is a third row: 90px to 71px. Deliberately one narrow band rather than a change to the 620px rule, because the profile is not monotonic and chasing every point of it would mean tuning to the exact pixel widths of eight controls.

  Net at 360x740: **about 77% down to about 61%**. At 1280x900 it is unchanged at about 26%, which is the honest outcome - the column layout is already the right shape there, and peek is what answers it.
- **The bottom sheet made two latent bugs live, and both are about what else is down there.** A dropdown with no room below flips *upward*, and `.wt-panel` is `position: fixed` - a stacking context - so `.wt-suggest-list`'s own `z-index` could not lift it above `.wt-dock`, which was a later sibling of `#wt-root`. Invisible in the column layout, where a right-hand panel and a bottom-left dock never share space; at 360x480 two of the six Shadow presets hit-tested to `.wt-hint`. The dock is now painted *before* the panel, which fixes the class rather than the instance. Separately, `placeShape` drops a shape where you clicked and selects it, so a click in the lower half of a narrow page produced a shape immediately buried by the sheet that opened over it - and clearing only the sheet moved it into the band the dock occupies, the same bug one obstruction further up. `revealBehindSheet` therefore asks both rendered boxes, and does it two frames later, because `--wt-panel-h` is written from a ResizeObserver and the dock's `bottom` calc resolves on the recalc after that.
- **`H` needed a voice.** Peek has no button, so the key is the only way in - which meant pressing it inside a field did nothing and said nothing, and the commonest way to end up in a field is clicking a page element that sits under the panel and hitting whichever control was painted there. The guarded branch now says so. The note also carries `role="status"`, the Overlay's first live region: peek takes 93 controls out of the accessibility tree at once and a screen reader was told nothing. And because `visibility: hidden` makes the chrome non-focusable, the browser drops focus to the body - correct during a peek, and destructive after one, so the keyboard position is stashed and restored unless the peek ended by a click on the page.
- **Three cascade bugs of one kind turned up doing this, and the file now says so out loud.** This stylesheet declares most of its `@media` blocks around line 200 but its components much further down, so any block written up there loses at equal specificity to the base rule below it. That silenced the short hint at every width, left the bottom sheet applying `left: 0` but not `width` or `top` (a 270px column pinned to the left edge, a layout no rule in the file describes), and had made the dock's own 613px cap inert since it shipped in 0.7.1. The last one is the instructive one: `right: 294px` *did* apply, so the rule looked half-alive, and with left, right and width all non-auto the box is over-constrained and `right` is silently dropped. The short-spelling defaults are now gathered at the top with a note saying why, and anything overriding `.wt-panel` or `.wt-dock` lives at the end of the file.

  A later audit found a **third shape** of the same trap, and two more instances of it. Source order is only half the problem: `#wt-scope` is `wt-scope wt-suggest` and `#wt-scope-list` is `wt-suggest-list wt-band-list`, so the losing declaration is not the one written earlier but the one on the class the reader did not have in mind. `.wt-band-list { width: 258px }` lost to `.wt-suggest-list { width: 236px }`, ellipsising band conditions 22px early; `.wt-scope { gap: 6px }` lost to `.wt-suggest { gap: 4px }` and had never once applied, with a `@media (max-width: 700px)` block dutifully re-stating the value that was already winning. The worst instance was neither: `.wt-bar-wrapped .wt-palette` re-anchors the shape palette with `left: 12px` but never releases the `right: 0` it inherits, so on a wrapped bar the box stretched between both edges - 608px of opaque, `pointer-events: auto` panel painted across the page, and at 620px it took the properties panel's top-right click. That rule exists *specifically* to stop the palette eating panel clicks. It had moved the theft from one edge to the other, and shipped that way in 0.7.1.
