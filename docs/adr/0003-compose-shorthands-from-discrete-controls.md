# Composed shorthands: three controls write one declaration, seeded so that every control is visible

Bringing `border` to existing elements (0.4.0) is the first property in the overlay's `CONTROLS` table that a user cannot author with a single control - a border is a width, a style and a colour. We decided the three controls **compose one `border` declaration**, and that touching any one of them on an element with no border **seeds the other two** so a border renders immediately. The obvious alternative - three controls emitting three longhand patches (`border-width`, `border-style`, `border-color`) - was rejected because two of the three are individually invisible, and invisibly-recorded patches are the one failure mode this codebase keeps re-learning.

**Why longhands are worse, despite being the literal truth.** CSS initial values are `border-style: none` and a width that computes to `0` while style is `none`. So on an element with no authored border, setting *only* a colour renders nothing, and setting *only* a width renders nothing - two of the three controls appear broken the first time anyone uses them. Worse, `CSS.supports("border-color", "#ccc")` is `true`, so the overlay's invalid-value gate in `writeControl` passes the value through and `record()`s it. That is a patch for a change the page never showed, reaching real source on reconcile - exactly the phantom-patch class the gate exists to prevent, arriving through the front door instead.

**Why seeding does not break ADR-0001.** Seeding means the emitted patch carries a `1px` and a `solid` the user never explicitly chose, which looks like the overlay inventing intent. It isn't: the seeded values are applied to the live preview *first*, so the patch describes exactly what was on screen when the user stopped. Capture-intent means capture what you *saw*; emitting a bare `border-color` would record something the preview never displayed. The precedent is ADR-0002's shape creation, which seeds `e.changes` with a full initial style snapshot for the same reason - so a control always has a real value to read and write, and the patch is self-contained even if the user never touches a control. The seeded colour needs no invention at all: computed `border-color` defaults to `currentColor`, so the swatch already shows the element's own text colour.

**An asymmetric border is detected by the computed shorthand serialising to the empty string.** Verified in a browser prototype: `getComputedStyle(el).border` returns `"2px dashed rgb(255, 0, 0)"` for a uniform border and `"0px none rgb(0, 0, 0)"` for none, but `""` whenever the four sides differ. That is an exact, browser-provided test, so no parsing of a multi-value `"0px 0px 1px"` width is needed. **When exactly one side is visible the controls edit that side** and emit `border-bottom` (etc.) instead - bottom rules under headings are everywhere on the editorial sites webtweak targets, and composing a full `border` there turns a divider into a box. **When several sides differ the controls are disabled** with an explanatory tooltip, following the existing precedent that disables width/height on non-replaced inline elements rather than letting a user record a patch the element won't honour.

**"Border" and "Stroke" are now distinct terms.** A shape's line is an SVG `stroke` (ADR-0002 chose SVG precisely so a real outline renders on every shape kind); an element's is a CSS `border`. The shape controls' labels therefore become **Stroke** / **Stroke width** - a label-only change, since their `prop` was already `stroke`/`stroke-width`. The new Border group is hidden for shapes, because a CSS border on the `<svg>` wrapper would draw a rectangle around a triangle, the exact failure ADR-0002 avoided. The shape's **Radius** keeps its name: unlike stroke-versus-border, `rx` and `border-radius` are the same concept in the same units, so renaming it would add noise without removing ambiguity.

## Consequences

- **The `CONTROLS` table's one-control-one-property assumption is bent.** Three entries share `prop: "border"`, so each control's handler must compose from the current value of all three fields rather than writing its own in isolation - otherwise they silently overwrite each other's contribution to the same declaration. The failure mode produces a valid-*looking* patch, so this is where a review of 0.4.0 should start.
- **Reconcile receives a declaration containing values the user did not individually set.** That is intended, and the reconcile skill keeps its usual freedom to tidy the declaration into house conventions - but it must *not* normalise a per-side `border-bottom` into an all-sides `border`, because the side is the intent.
- **An element with several differing borders is not editable in the overlay**, by choice. Per-side controls would roughly triple the densest part of the panel for an uncommon case; the user is told, rather than silently given a box where they had a rule.
- **The pattern generalises but is deliberately not generalised yet.** `outline`, `text-decoration`, `transition` and `transform` have the same shape. Nothing here is factored into a reusable composed-control abstraction until a second property actually needs it - one call site is not a pattern.
- **`box-shadow` deliberately does *not* use this pattern.** Discrete shadow controls would need four lengths, a colour and an inset flag, and the colour is almost always translucent while the overlay's swatch is opaque hex. It stays a text field with a suggestion list of presets - which is also why the font picker's suggestion-list widget is built first and reused.
